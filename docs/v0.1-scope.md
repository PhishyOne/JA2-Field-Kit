# Read-only v0.1 scope

## User-visible goal

The smallest useful version is:

`open .sav -> identify what we can support -> campaign summary -> roster -> merc stats`

Nothing in v0.1 writes to a save.

The [Issue #36 core rewrite kernel](marksmanship-edit-kernel.md) is separate from
this product scope. Production editing remains disabled and Android remains
read-only. Its serialized profile/base marksmanship field is not established as
the hired merc's live/current tactical marksmanship.

## Acceptance path

Given an admitted save compatible with the normal v103 / Build `04.12.02`
non-Linux layout, v0.1 should be able to:

1. Read the file without modifying it.
2. Detect the supported layout/version by binding header selection to body
   rotation identity; report producer family only if separate byte evidence
   establishes it.
3. Decode the campaign-level fields needed for a compact summary.
4. Locate/decrypt the merc profile table using the correct header-selected encryption path.
5. Parse the roster and reproduce the known **18 active/owned mercs** from the fixture.
6. Show each roster merc's name and core stats.
7. Fail explicitly on unsupported, malformed, or truncated input instead of returning plausible garbage.

## Core stats for the first screen

Start with the standard profile stats already proven useful during the prior decode:

- health
- agility
- dexterity
- strength
- leadership
- wisdom
- experience level
- marksmanship
- mechanical
- explosives
- medical

Do not add traits, kills, salary, inventory, or active-soldier condition merely because the profile structure contains them. They are follow-on slices once the first path is reliable.

## Implementation sequence

### Slice A: fixture-backed header map

- add a test fixture or private-fixture test path,
- document exact offsets used,
- parse version + minimal campaign summary fields,
- create negative tests for short/truncated input.

### Slice B: layout/encryption compatibility

- encode the header-state rule that selects normal save encryption,
- bind the selected index to recovered body rotation through independently
  admitted non-secret identity evidence,
- keep producer family `UNKNOWN` where Reborn and Stracciatella are
  byte-indistinguishable at this layer,
- keep unknown formats explicit.

### Slice C: profile-table reader

- locate/decrypt all 170 profile records,
- parse the independently evidenced names, profile health fields, and
  first-screen stats,
- establish roster membership only from separate evidence, without treating
  the 170-entry profile table itself as the player's roster.

All three bullets are now implemented for the bounded normal non-Linux Build
`04.12.02` path. The profile records did not provide independently verified
evidence sufficient to reproduce hired/player membership, so membership is
established by a narrow crossing into the canonical 20 player `SOLDIERTYPE`
slots. That crossing interprets only slot identity, player/team/vehicle flags,
profile identity, and mandatory checksum inputs. It validates and skips opaque
path and keyring tails, excludes vehicles, then joins profile IDs by record
index. The header merc count is a post-scan cross-check rather than framing
authority.

Public synthetic tests include an exactly 18-merc construction. Issue #6 stays
open until a candidate plus authorized private acceptance reproduces the known
roster.

### Slice D: stable core API

`Ja2SaveInspector.inspectV01(bytes)` is the presentation-facing acceptance
surface. One call snapshots the caller's bytes, performs detection/admission
exactly once on a separate detector copy, rejects detector mutation or runtime
failure with bounded codes, parses only the untouched original snapshot, and
either returns:

- `SaveInspectionV01Result.Success`, containing sanitized format/version/layout/
  compatibility facts, the header-backed `CampaignSummaryV01`, and the verified
  roster with core profile stats; or
- `SaveInspectionV01Result.Failure`, containing the same bounded format facts
  plus a failure kind and diagnostic enum.

The v0.1 result does not expose descriptions, input bytes, offsets, framing
stages, selector indices, rotation material or digests, encryption details, or
internal parser exceptions. Unknown, unsupported, truncated, inconsistent, and
admitted-but-corrupt inputs are distinguishable without payload-bearing error
messages. Existing research-oriented detector and guarded layout methods remain
available for compatibility, but presentation consumers should use
`inspectV01`.

The campaign summary is deliberately limited to already mapped serialized
header facts: day, hour, minute, current sector coordinates, player merc count,
and balance. The producer family remains `UNKNOWN` unless an independent byte
discriminator is established.

## Explicit non-goals for v0.1

- full active-condition `SOLDIERTYPE` parsing beyond the membership/checksum crossing
- current wounds/condition beyond profile health fields
- tactical inventory
- ammo/equipment
- assignments/paths
- sectors beyond the campaign summary
- mines/economy detail
- any editing
- save writing or in-place mutation
- Android framework or UI code in `core`
- automatic support for JA2 1.13

## Gate before editing

Editing starts only after a supported save can be parsed reliably and the
per-format no-op and verification requirements in
[transactional-edit-safety.md](transactional-edit-safety.md) are satisfied.

If write support is later authorized, the transaction sequence is:

`enforce core source-size admission -> structurally admit requests/assertions into an immutable bounded snapshot before bulk copying or proportional work -> establish observable identity and enforce any tighter capability bound -> format/edit-admit and parse source -> semantically admit requests and bound/build the verification plan -> apply logical changes in memory -> serialize with the strictest applicable bounded private writer -> re-admit/reparse candidate -> verify requested changes and critical unchanged facts -> complete bounded provenance and produce verified candidate`

The 16 MiB source/candidate ceiling remains unchanged. Core must additionally
own finite operation/assertion counts (duplicates counted before deduplication),
variable-component and aggregate input/canonical budgets, and total expanded
plan/report/provenance budgets. Admission itself must be bounded, accounting
overflow-safe, and failures terminal with bounded diagnostics. The future public
editor contract must fix concrete limits with workload, worst-case expansion,
and memory/CPU evidence before any edit capability is enabled; an unspecified
required limit keeps editing disabled. Callers/adapters cannot raise these
limits; capabilities may only tighten them.

Only after that transaction succeeds may a separate output-placement operation
create a new file by default. It requires protected private staging, staged
size/hash verification against candidate provenance, qualified atomic no-replace
publication of the complete object to an absent destination, then published
byte/binding verification and required data/namespace durability before success.
Cross-domain transfer requires destination-domain staging or proven equivalent
semantics; unsupported publication fails closed. Ambiguous publication outcomes
preserve uncertainty and recovery evidence until destination reconciliation
before further mutation, with no blind retry or unsafe cleanup. The original
file is never the default write target.
Replacement is a separate, explicit later operation, supported only with a
core verified immutable candidate/provenance, exact destination authority, and
operation-owned private staging protected in bytes, identity, and binding from
verification through atomic installation, including the destination-guard
handoff. The qualified guard must cover relevant competing writers and
destination content/name binding continuously from final expected-original
comparison through backup creation/verification/durability, commit, installed
verification/durability, persisted outcome/recovery recording, and release.
Create the independent backup from the guarded original; verify and protect its
bytes/object/binding and bind recovery evidence to that exact original and
transaction. Backup data/namespace durability and recoverable transaction
association must precede any destination mutation. Success requires installed
byte/binding verification, installed data/namespace durability, and persisted
outcome/recovery recording while guarded, not merely atomic commit or API return.
Otherwise replacement is unsupported and fails closed; separate create-new/Save
As may remain available only if its own publication contract qualifies.
Before mutation, failure leaves the destination untouched by the operation.
Once commit may have occurred, missing evidence means UNCERTAIN: retain durable
backup and available staging/evidence, with no blind retry, restoration, deletion,
or cleanup. Crash/guard loss requires reacquiring the guard and reconciling all
artifact identities/hashes, persisted evidence, and competing changes before
mutation. Restoration requires a separate guarded conditional replacement with
durable verified backup authority bound to the exact original. Cleanup requires
proven ownership and disposal authority protected through disposal; success does
not authorize backup deletion unless separately proven safe with no remaining
recovery obligation.
